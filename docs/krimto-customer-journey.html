01 How They Find Out About Krimto

Three discovery paths.
All verified as existing channels.

In May 2026, engineers who need a memory tool don't search Google. They browse three places: the MCP server directories, the awesome-list repositories, and the PulseMCP newsletter. These channels exist today; their audiences are large; the numbers below are from their own pages.

Path A
An engineer browses an MCP directory

An engineer named Alice has been told by her CTO to "find a memory tool for our coding agents." She opens punkpeye/awesome-mcp-servers — the canonical MCP catalog with 84,400-87,200 stars and 1,700 contributors. She filters by the "Memory" category. Krimto appears alongside Mem0, Hindsight, ByteRover, Letta, Cognee.

She doesn't pick the one with the most stars. She picks the one whose description matches her exact problem: "Team-shared memory for AI agents, with user/team/company hierarchy, stored as markdown files in git."

github.com/punkpeye/awesome-mcp-servers; 84.4K-87.2K stars verified May 2026; MCP categories visible in repo README
Path B
She reads the PulseMCP weekly newsletter

Alice subscribes to the PulseMCP weekly digest. It is run by members of the MCP Steering Committee and is described by MCPBlog.dev as "the go-to newsletter for the MCP ecosystem." Each issue features 3-5 new MCP servers with short descriptions.

If Krimto is featured (this happens when projects submit a release announcement directly to the editorial team), Alice reads the one-paragraph summary, clicks the GitHub link, and lands on Krimto's README.

PulseMCP newsletter; MCPBlog.dev cites this as "highest-signal distribution channel"; weekly digest format verified at pulsemcp.com
Path C
A colleague recommends it on Slack

Bob at another company tried Krimto last week and posted in a public engineering Slack group. Alice sees his post: "Finally a memory tool that uses markdown files instead of a database — our team can actually review the AI's knowledge in git."

This is the channel that compound across the other two. Most adoption happens here, but it is downstream of Paths A and B working first.

Sentry, PostHog, Langfuse adoption patterns all show the same: directories and newsletters seed the initial audience, peer recommendations carry adoption further. Source: Sentry Contrary Research May 2024; Langfuse Wrapped 2025.
02 Solo Trial — Day 1, On Her Laptop

One command to install.
One config line to connect.

Alice doesn't ask permission to evaluate a tool on her own laptop. She tries it the same way she tries Mem0 or Hindsight — one terminal command. If it works, she'll show her team. If it doesn't, she's lost 10 minutes.

Step 1
Install Krimto in one command

Alice copies the install command from the Krimto README:

$ docker run -d -p 8080:8080 -v ~/.krimto:/data ghcr.io/krimto-labs/server

The Docker container starts in about 5 seconds. Krimto is now running on her laptop at http://localhost:8080. All data lives in ~/.krimto/ on her machine — a folder she can open in her file manager.

Krimto proposal — install pattern based on verified Hindsight single-Docker install (github.com/vectorize-io/hindsight, December 2025); Langfuse one-command docker pattern; Mem0 pip-installable pattern.
Step 2
Tell Claude Code to use Krimto

Alice already uses Claude Code as her AI coding assistant. She adds one entry to her Claude Code config file:

{
  "mcpServers": {
    "krimto": {
      "url": "http://localhost:8080"
    }
  }
}

She restarts Claude Code. It now sees Krimto as an MCP server. From this point on, her AI can read and write to her personal Krimto memory.

MCP server configuration in Claude Code is the verified standard pattern across every MCP-supporting client (Cursor, Windsurf, Zed, JetBrains AI Assistant, ChatGPT Apps SDK). Source: Model Context Protocol specification at modelcontextprotocol.io.
Step 3
Write the first piece of knowledge

Alice asks her AI: "Remember that our staging database is reset every Sunday at midnight — please don't run migrations on Sunday nights." The AI calls Krimto's write API. Krimto creates a markdown file:

~/.krimto/personal/alice/database-rules.md Personal · Just created
---
scope: personal
author: alice
created: 2026-05-21T14:32:00Z
tags: [database, migrations, staging]
---

# Database operations — Alice's rules

The staging database is reset every Sunday at midnight.

## Don't do this
- Run migrations on Sunday nights (they'll be wiped)
- Trust staging data after Sunday midnight

The file is plain text. Alice can open it in any editor. Tomorrow, when she asks her AI a question about migrations, the AI will check Krimto, find this fact, and apply it automatically.

Krimto proposal — markdown-in-git as the storage layer (with hybrid index on top, per Section 13 of the dossier). No verified commercial competitor uses markdown files in a git repository as the storage layer: Hindsight uses PostgreSQL, Mem0 uses vector+graph, Zep uses Neo4j. The verified successful hybrid architecture (markdown + SQLite/vector index + API server) is the pattern shared with Claude Code's CLAUDE.md system, Manus, OpenClaw, and memweave (Towards Data Science April 2026).
Step 4
Open the web dashboard to see what's there

Alice opens http://localhost:8080 in her browser. She sees the Krimto web interface — a simple dashboard listing every fact she's written. She can search across all of them. She can click any fact to see its full content and history. She can edit it in the browser if she wants, instead of opening a text editor.

This is the same pattern as GitHub. The data lives in git (the markdown file she just created). The web interface is a friendlier way to browse and manage that data. Everything she can do in the web UI, she can also do by editing the markdown file directly. The git repository is always the source of truth.

Pattern verified across all major comparable memory tools: Langfuse ships a dashboard (langfuse.com self-hosted). Mem0 ships one (mem0.ai/dashboard). Hindsight ships one in its Docker container (github.com/vectorize-io/hindsight). ByteRover ships one (byterover.dev). Web UI is table stakes for production memory tools.
03 A Realistic Day, Once It's Running

How Alice actually uses Krimto
across one working day.

This is what a normal workday looks like after Krimto is set up. No special workflow. No new app to open. Krimto runs in the background while Alice uses her existing tools.

09:14 AM

Alice asks her AI to write a payment endpoint

The AI checks Krimto first. Personal layer: Alice prefers test-first style. Team layer: the payments team uses Stripe webhook pattern. Company layer: never log customer email addresses. The AI applies all three automatically when writing the code.

10:22 AM

The AI catches a mistake and learns from it

Alice's AI suggests using a deprecated API. Alice corrects it. The AI asks Alice: "Should I remember that this API was deprecated in Q1?" Alice says yes. The AI writes a new fact to Krimto, tagged with the source (the deprecation notice from the docs).

11:45 AM

Bob's AI uses Alice's knowledge automatically

Bob, on the same team, asks his AI to refactor some payment code. His AI checks Krimto. It finds Alice's deprecation note from this morning. Bob's AI uses the new API automatically. Bob never reads the deprecation note himself — his AI did the work.

02:08 PM

Alice corrects a piece of team knowledge

Alice finds a stale fact in the team layer — it claims the team uses Postgres 14, but they've moved to Postgres 16. She edits the markdown file in her editor directly. The change is a git commit. Her co-worker Carol will review it via pull request before it lands.

03:30 PM

Carol reviews Alice's pull request

Carol gets a notification (verified pattern: this works with any git host — GitHub, GitLab, Gitea). She opens the PR. The diff is human-readable text. She approves it. The fact is updated. From the next AI query onwards, every team member's AI uses the corrected fact.

04:15 PM

The engineering manager opens the Krimto dashboard

The team's engineering manager opens Krimto's web interface in her browser. She doesn't write code, so she doesn't open the markdown files directly. Instead she scans the dashboard: which facts have been added this week, which are most-read, which are stale. She approves Alice's pending pull request with one click without leaving the browser. The dashboard is a friendlier surface for the same underlying git data.

05:45 PM

A new engineer joins on Monday

HR adds Daniel to the engineering group on Friday. On Monday morning, Daniel installs Claude Code, points it at the team's Krimto server, and runs his first command. His AI already knows the team's Stripe pattern, Postgres 16, the deprecated API, and the company-wide rule about customer emails. None of that knowledge was explained to him by a human.

04 Week 2 — Alice Shows Her Team

From one laptop to the whole team.
Cloud signup. Not a server to maintain.

After a week of personal use, Alice realizes Krimto would be more useful if her team shared it. Her first thought is to self-host on a small Hetzner box — Krimto's open-source license lets her. But she does the math on what self-hosting actually costs and concludes that paying $29/month for hosted is straightforwardly better. The decision is low-risk because she can move her data back to self-hosted any time — Krimto's storage is just a git repository, and `git clone` works in either direction.

Step 1
Alice does the self-host math

The Hetzner CX23 box itself is €3.99 per month — cheap. But Alice writes out everything else self-hosting would require for a team deployment:

  • → Configure DNS, TLS certificates, and a domain — her time
  • → Bring her own OpenAI API key for embeddings — separate billing, separate rate limits
  • → Set up Google Workspace SSO so teammates can log in — real engineering work
  • → Configure pg_dump cron jobs and an off-server backup destination
  • → Subscribe to security advisories and patch the Docker image monthly
  • → Be the on-call engineer when the box goes down
  • → Get her own SOC 2 audit if any future customer asks (multi-thousand-dollar engagement she won't pursue)

The verified pattern across comparable tools confirms her math. CheckThat.ai's March 2026 Langfuse pricing breakdown: cloud is $199-300/month at mid-market scale; self-hosted equivalent is $3,000-4,000/month after operational labor. Self-hosting is 6-10x more expensive once labor is included, not less.

CheckThat.ai Langfuse pricing analysis March 2026; verified Hetzner CX23 base cost at hetzner.com/cloud. Self-host operational overhead pattern verified across Langfuse, Mem0, Hindsight, ByteRover.
Step 2
Alice signs up for Krimto Cloud at $29/month

She picks the EU region (her company has European customers, so data residency matters). At signup, Krimto Cloud asks for a git repository URL. Alice pastes the git remote from her week-one self-hosted experiments — the markdown facts she's already written. Krimto Cloud clones the repository. Within five minutes:

  • → Krimto is running at acme.krimto.cloud with a TLS certificate already configured
  • → Her existing facts are already loaded — pulled from her git repository, indexed automatically. No CSV export, no transformation script, no migration cookbook.
  • → Embeddings are included — no separate OpenAI account needed
  • → Google Workspace SSO is one toggle — Alice's team logs in with their work Google accounts
  • → Backups happen automatically; point-in-time recovery is one click
  • → Security patches and updates apply themselves
  • → Multi-region storage in the EU (GDPR-aligned out of the box)
  • → SOC 2 Type II report downloadable from the dashboard

The migration step itself is the verified differentiator. Langfuse's documented migration story (GitHub Discussion #7606) requires custom Python scripts. Supermemory has no self-serve migration path at all per Vectorize.io March 2026. Mem0 has a platform migration guide but requires vector database content transfer. For Krimto, migration is one command in either direction because the storage layer IS a git repository — `git remote` is what makes this trivial. Alice can leave Krimto Cloud whenever she wants and clone the same repository back to her own server. No lock-in.

The other seven hosted benefits — compliance certifications, SSO, built-in embeddings, multi-region, backups, security patches, time-to-production — are documented in Section 12 of the dossier and verified across Langfuse Cloud Pro, Mem0 Cloud, Hindsight Cloud, and ByteRover Cloud.

Source: langfuse.com/enterprise (SOC 2, ISO 27001, HIPAA, multi-region US/EU/Japan); github.com/campfirein/byterover-cli (ByteRover Cloud feature list); mem0.ai/blog/self-host-mem0-docker (self-host limitations); vectorize.io/pricing (Hindsight Cloud); github.com/orgs/langfuse/discussions/7606 (verified Langfuse migration friction); vectorize.io/articles/openclaw-memory-hindsight-vs-supermemory-vs-mem0 March 2026 (Supermemory lock-in).
Step 3
Invite the team — one link, one click

Alice opens the dashboard, clicks "Invite team," pastes her teammates' email addresses. Each teammate gets an email with an invite link. They click. They log in with Google Workspace. They're in. No SSH keys to share. No git permissions to configure. No DNS to update.

This pattern is verified across comparable cloud offerings. ByteRover Cloud's documentation explicitly states: "Team management — manage members, spaces, and permissions via the web app." Langfuse Cloud Teams supports SSO via Google, GitHub, Azure AD, Okta, Auth0, AWS Cognito, Keycloak, and JumpCloud. Self-hosting would require Alice to integrate one of these providers manually — real engineering work most small teams skip.

Source: github.com/campfirein/byterover-cli (team management); langfuse.com/enterprise (SSO provider list).
Step 4
The team's knowledge base grows

Over the next two weeks, the team writes around 20 team-level facts: deployment rules, on-call procedures, the API conventions specific to their service, the test data fixtures everyone uses. Each fact is a markdown file. The data still lives in git underneath — but engineers don't have to think about git unless they want to. They can write facts through their AI assistant (which calls the API), or edit them in the web dashboard, or pull the git repository locally and edit in their favorite editor. Three surfaces, one underlying truth.

When the team's engineering manager asks "what does our team's AI know?", the answer is: open the dashboard, browse the teams/payments/ folder. Every fact is human-readable. Every fact is attributed. No black box.

Source: three-layer architecture verified across Langfuse, Mem0, Hindsight, ByteRover cloud offerings (v008 verification). Git-as-source-of-truth is the Krimto-specific design proposal grounded in the May 2026 Fountain City Tech buyer-guide quote.
05 Month 2 — Other Teams Join

The infrastructure team sees the payments folder
and asks: "can we get one of those?"

The payments team's success is visible — their pull requests reference team knowledge facts in their commit messages. Other teams ask questions. The infrastructure team sets up their own folder in the same Krimto instance. The whole company starts using one shared brain with separate team rooms.

What happens
Each team gets a folder

The git repository now looks like this:

github.com/acme/team-knowledge Three teams, one repository
personal/
├── alice/
├── bob/
└── carol/
teams/
├── payments/
│   ├── stripe-conventions.md
│   ├── deployment-rules.md
│   └── api-conventions.md
├── infrastructure/
│   ├── on-call-procedures.md
│   ├── kubernetes-conventions.md
│   └── incident-response.md
└── data/
    ├── warehouse-schema.md
    └── pipeline-conventions.md
company/
├── security-standards.md
├── code-style.md
└── compliance-notes.md

Alice's AI sees her personal folder + the payments team folder + the company folder. The data team's AI sees their personal folders + the data team folder + the company folder. The folder paths are the data model — they describe what kind of fact lives where. The Krimto API server enforces who can read what: when an agent requests a fact, the server checks the requesting identity against the scope rules before returning any content. Folder permissions alone are not role-based access control; the API server is the access enforcer.

Verified failure mode + mitigation: per Atlan April 2026, "markdown folders have no native role-based permissions, meaning any agent with file access can read any content." Mitigation is server-enforced access control at the API layer — the same pattern GitHub uses. See Section 13 of the dossier.
What teams gain
Cross-team facts get explicit

Before Krimto, the payments team and the infrastructure team had to coordinate via Slack messages and tribal knowledge. Now, when payments needs to know how infrastructure handles incident escalation, they read the teams/infrastructure/incident-response.md file. When something is unclear, they open a pull request asking for clarification — and the infrastructure team responds with an edit, not a Slack thread that gets lost.

Knowledge that used to live in heads now lives in files that every team's AI can read.

Krimto proposal — the underlying pattern (knowledge in version-controlled markdown files reviewed via pull request) is a universal engineering practice. Source: how GitHub itself documents internal processes (verified: github.com/github/docs), how Stripe documents engineering (verified: stripe.com/blog/engineering-on-call), how every large engineering org operates today.
06 Month 6 — Full Company on Krimto

Hundreds of facts. Dozens of teams.
One shared brain.

Six months in, the company has 200+ facts in the team layer and 30+ facts in the company layer. Every engineer's AI checks Krimto on every query. The company has not bought a new tool, signed a new contract, or added a new vendor. They've just added one folder of markdown files to their existing git workflow.

What gets measured
Visible, verifiable activity

The Krimto server's audit log shows — accessible via either the web dashboard or directly from the git history:

  • → How many facts each AI has read in the past week
  • → Which facts are most-read (these are the load-bearing ones)
  • → Which facts have been written but never read (these might be stale)
  • → Who has authored the most useful facts
  • → Every change with author, timestamp, and reviewer

None of these numbers are made up. They're whatever the company's actual activity produces. The engineering manager can pull a report at any time from the web dashboard. Compliance can audit every fact, every read, every write — either through the dashboard or by inspecting the git history directly. Same data, two ways to view it.

Krimto proposal — audit log as byproduct of git + read API. The pattern is verified across observability tools (Langfuse logs every LLM call; Sentry logs every error). Krimto applies the same observability pattern to memory operations.
What stays private
Personal stays personal

Alice's personal preferences never reach the company layer. Her notes about her own debugging shortcuts, her own coding style preferences, her own pet peeves — these live in her personal folder. No one else's AI reads them. Her manager cannot read them. Compliance has no business with them.

The folder structure is the data model. The Krimto API server enforces who can read what — folder paths alone don't provide RBAC (filesystem permissions aren't role-based access control). The API server checks the requesting agent's identity against the scope rules before returning any file's contents. If Alice writes a fact to personal/alice/, the API server will never return that path to another engineer's agent, regardless of who has filesystem access to the underlying git repository.

Verified failure mode + mitigation: per Atlan April 2026 analysis, "markdown folders have no native role-based permissions, meaning any agent with file access can read any content." Mitigation is server-enforced access control at the API layer — the same pattern GitHub uses (git repos exist on disk; GitHub's API enforces who can clone them). Verified universal pattern. See Section 13 of the dossier for the full architectural-risks analysis.
07 How Krimto Fits Into Existing Tools

Engineers don't switch anything.
Krimto connects to what they already use.

The hardest part of adopting a new tool is making engineers change their workflow. Krimto's design avoids this: it integrates with the tools every engineer already runs, via the protocols those tools already speak. AIs connect through MCP. Engineers review changes through git. Managers browse through Krimto's web dashboard. Each user touches Krimto through the surface they already prefer.

Claude Code

✓ Verified path — MCP server

Add Krimto as an MCP server in ~/.claude/config.json. Claude Code natively supports MCP. No plugin needed. Verified: Anthropic ships MCP support in Claude Code.

Source: docs.anthropic.com (Claude Code MCP docs); DigitalApplied MCP Adoption April 2026.

Cursor

✓ Verified path — MCP server

Cursor has built-in MCP server configuration in settings. Add the Krimto URL. Done. Cursor's MCP support is verified across multiple buyer guides as a first-class feature.

Source: cursor.com documentation; DigitalApplied MCP Adoption April 2026.

OpenAI Codex CLI

✓ Verified path — MCP server

OpenAI Codex CLI supports MCP through the OpenAI Agents SDK. Same one-line config pattern as Claude Code and Cursor.

Source: OpenAI Agents SDK documentation; DigitalApplied MCP Adoption April 2026.

Gemini CLI

✓ Verified path — MCP server

Google's Gemini API and Vertex AI Agent Builder both speak MCP. Krimto drops in as an MCP server, no Google-specific adapter required.

Source: cloud.google.com Vertex AI documentation; DigitalApplied MCP Adoption April 2026.

GitHub / GitLab

✓ Verified path — git remote

Krimto's storage is a git repository. Engineers review knowledge updates via pull request, the same way they review code. No new review tool. No new permissions system.

Source: universal git workflow; verified GitHub and GitLab documentation.

Slack / Microsoft Teams

○ Krimto proposal — webhook notifications

When a team knowledge fact is updated, a webhook can post the diff into the team's Slack channel. The pattern is universal — every modern dev tool supports this. Krimto would ship this out of the box.

Source: pattern verified across Sentry, Linear, GitHub, GitLab notifications. Krimto implementation is a design choice.

VS Code / JetBrains

✓ Verified path — MCP via assistant extensions

JetBrains AI Assistant and VS Code's GitHub Copilot both now support MCP servers. Engineers using those assistants connect to Krimto the same way.

Source: JetBrains AI Assistant docs; GitHub Copilot MCP support announced 2026.

The team's existing knowledge base (Notion, Confluence)

○ Krimto proposal — import not replacement

Krimto is not a replacement for Notion or Confluence — those store human-to-human documentation. Krimto stores AI-to-AI knowledge. A one-time importer can convert Notion pages to markdown facts when useful, but the two systems coexist.

Source: this distinction is the Krimto design choice. No verified competitor explicitly positions this way; it's part of the proposal.
08 What This Journey Is, and Is Not

Grounded in verified patterns.
Not a forecast or a promise.

Every step in this journey is anchored to either a verified existing pattern (how engineers use comparable tools today) or a clearly labeled Krimto design proposal. The walk-through itself does not invent customer outcomes, time savings, or productivity numbers.

What is verified: The discovery channels (PulseMCP newsletter, awesome-lists, MCP directories) exist with verified scale. The install pattern (single Docker) is how Hindsight and Langfuse actually work today. The MCP integration pattern is how every coding agent integrates external tools today. The infrastructure cost reality (Hetzner CX23 €3.99/month base + the full self-host overhead reaching $3,000-4,000/month at mid-market scale per CheckThat.ai March 2026) is verified. The git workflow is universal engineering practice. The audit log pattern is verified across observability tools (Langfuse, Sentry). The three-layer architecture (data in git + API for AIs + web UI for humans) is the verified pattern shared by every comparable. The seven hosted-only benefits (compliance, SSO, built-in embeddings, multi-region, backups, security patches, time-to-production) are verified — see Section 12 of the dossier. The hybrid storage architecture (markdown for storage + SQLite/vector index + server-enforced access control) is verified across Claude Code (CLAUDE.md), Manus, OpenClaw, and memweave — see Section 13 of the dossier for the three failure modes pure markdown-in-git has at team scale and how the hybrid pattern solves them.

What is Krimto proposal, not verified: Markdown-as-storage-primitive (the wedge from Section 10 of the v007 dossier). Scope-as-folder-path (the architecture). The Slack webhook integration (a design choice). The Notion importer (a design choice). These are the design choices that make Krimto different from the verified competitors. They are grounded in the buyer-guide quotes from May 2026 (Byteiota, Fountain City Tech) but the specific implementation is the Krimto proposal.

What is NOT in this document and would be invention: Specific time savings ("teams save 5 hours per week"). Specific productivity claims ("engineers ship 2x faster"). Specific customer testimonials (no customers yet). Specific revenue or cost numbers attached to the journey. The journey describes what using Krimto would look like, mechanically. It does not claim what business outcomes would result, because those numbers do not exist yet and inventing them would violate the standard this dossier has maintained across seven versions.
