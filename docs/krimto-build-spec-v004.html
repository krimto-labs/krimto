01 Fact / file schema Tier 1

One markdown file per fact.
Frontmatter is mandatory.

Every Krimto fact is a single markdown file with YAML frontmatter. The frontmatter is the machine-readable metadata; the markdown body is the human-readable content. The schema below is anchored to memweave's verified production schema, extended with Krimto-specific fields for hierarchical scope and attribution.

Verified default — anchored to memweave

File schema

--- id: fct_01j2k3m4n5p6q7r8s9t0v1w2x3 # ULID, immutable scope: team/payments # required, see Gap 03 title: "Stripe webhook conventions" # required, <= 80 chars author: alice@acme.com # required, resolves via Gap 07 created: 2026-05-22T14:32:00Z # required, ISO 8601 UTC updated: 2026-05-22T14:32:00Z # required, mirrors created on first write reviewed_by: [] # optional, array of identities tags: [stripe, webhooks, payments] # optional, lowercase kebab-case source: "https://stripe.com/docs/webhooks" # optional, see Gap 14 supersedes: [] # optional, array of fact ids expires: null # optional, ISO 8601 or null --- # Stripe webhook conventions When handling Stripe webhooks, always verify the signature using the official `Stripe.Webhook.constructEvent` method before processing any payload data. ## Why Stripe documents signature verification as the primary defense against forged webhook events. Skipping it is a verified security mistake. ## Don't do this - Trust the payload before signature verification - Process events without idempotency keys

Field rules

FieldRule
idULID. Generated on creation. Never changes — facts retain their ID even when scope changes via git mv.
scopeMust match the file's git path. See Gap 03 for the canonical scope convention.
titleRequired. Maximum 80 characters. Used in dashboard listings and search results.
authorRequired. Identity in local-part@domain form (matches OAuth claim, see Gap 06).
created / updatedRequired. ISO 8601 UTC. Server-set on write, immutable by the client.
tagsOptional. Lowercase kebab-case. Indexed for filtering.
sourceOptional. URL or stable identifier. See Gap 14 for the full provenance model.
supersedesOptional. Array of fact IDs this fact replaces. Used for soft-deprecation without breaking history.
expiresOptional. ISO 8601. Fact is excluded from retrieval after this date but file remains in git history.

File naming

File names are slug-of-title with .md extension. Example: title "Stripe webhook conventions" → filename stripe-webhook-conventions.md. Filename collisions within the same scope folder are resolved by appending -2, -3, etc. The id field is the actual unique identifier; the filename is for human readability in the git diff.

Verified anchor: memweave uses memory/MEMORY.md for evergreen knowledge and memory/YYYY-MM-DD.md for daily logs. Krimto follows the same "markdown file per unit of knowledge" pattern, with frontmatter as the metadata layer (verified Towards Data Science April 2026). Frontmatter for AI memory is also the verified pattern in Anthropic's Claude Code CLAUDE.md (header section), Manus, and OpenClaw. Source: github.com/sachinsharma9780/memweave; SFEIR Institute Claude Code CLAUDE.md analysis 2026
Design decision: ULID (vs UUIDv4 vs sequential integer) is chosen because ULIDs are time-sortable, URL-safe, and 26 characters fit cleanly into filesystem operations. Builder may substitute UUIDv7 (also time-sortable) without architectural impact. The supersedes + expires soft-deprecation pattern is anchored to how memweave handles superseded facts in dated logs.
Cannot verify: Whether 80 characters is the right title length cap at scale. memweave does not enforce a title length; Krimto proposes 80 to keep dashboard listings tidy. Adjustable without breaking compatibility.
02 MCP tool surface Tier 1

Five tools. No more.

Krimto exposes five MCP tools. Tool count is anchored to the verified mid-range across comparables: Mem0 ships 4 tools, ByteRover/Cipher ships 4, Hindsight ships 3. Five is the minimum complete surface for hierarchical team memory with attribution.

Verified default — anchored to Mem0, Hindsight, ByteRover patterns

Tool surface

krimto_write(scope, title, body, tags?, source?, supersedes?) → { id, scope, path, commit_sha } krimto_recall(query, scopes?, limit?) → { results: [{ id, scope, title, body, score, author, updated }] } krimto_read(id) → { id, scope, title, body, frontmatter, history } krimto_supersede(id, new_title, new_body, reason) → { old_id, new_id, commit_sha } krimto_list_scopes() → { scopes: [{ path, fact_count, last_updated }] }

Tool semantics

ToolPurpose
krimto_writeCreate a new fact. Scope is required. Server determines author from auth identity. Returns the new fact ID and the git commit SHA. Fails if requester lacks write permission to the scope.
krimto_recallSearch across one or more scopes. If scopes omitted, searches all scopes the requester can read (per Gap 07 access rules). Uses hybrid retrieval (Gap 04). Returns ranked results with attribution.
krimto_readGet one fact by ID, including its full frontmatter and git history. Used after krimto_recall to retrieve full content if the snippet was truncated.
krimto_supersedeReplace an existing fact with a new one. Creates a new fact whose supersedes field references the old. Old fact is marked superseded but remains in git history.
krimto_list_scopesDiscover what scopes exist and what they contain. Returns only scopes the requester can read.

What is NOT a tool

  • No krimto_delete. Facts are never hard-deleted via the MCP API. Use krimto_supersede or set expires in a git-direct edit. This is intentional — git history is the audit trail; permanent deletion happens only via git history rewriting, which requires admin access through the web UI (see Gap 12).
  • No krimto_extract or auto-extraction tool. Krimto does not silently extract facts from conversation history. Writes happen only when an agent explicitly calls krimto_write. See Gap 11 for the agent write workflow.

The delete omission preserves git history as the audit log (Gap 04 attribution requires this). The auto-extract omission is the deliberate opposite of ByteRover/Mem0's automatic fact extraction — Krimto's hierarchical-team-memory positioning requires explicit, attributable writes rather than silently extracted ones (see Gap 11).
Cannot verify: Whether krimto_list_scopes is needed in MCP at all, or whether scope discovery should happen via the web UI only. Listed in the v0.1 spec because Hindsight's tool surface includes a discovery primitive; may be removable after measuring usage.
03 Scope path convention Tier 1

Three-level hierarchy. Path is the address.

Krimto uses a strict three-level hierarchy: user, team, org. Scope is encoded as a slash-separated path that maps one-to-one with the git repository folder structure. The path is the address; the folder is the storage location; the API server enforces access (per Gap 07).

Design decision — anchored to dossier Section 05 promise #02

Canonical scope syntax

user/<identity> # personal facts for one user team/<team-slug> # shared facts for one team org/<org-slug> # organization-wide facts # Examples user/alice@acme.com team/payments team/infrastructure org/acme

Repository structure

/ # git repository root ├── user/ │ ├── alice@acme.com/ │ │ ├── stripe-shortcuts.md │ │ └── debugging-notes.md │ └── bob@acme.com/ │ └── postgres-tips.md ├── team/ │ ├── payments/ │ │ ├── stripe-webhook-conventions.md │ │ ├── on-call-procedures.md │ │ └── api-conventions.md │ └── infrastructure/ │ └── kubernetes-conventions.md ├── org/ │ └── acme/ │ ├── security-standards.md │ └── code-style.md └── .krimto/ ├── members.yaml # user → team membership, see Gap 07 └── config.yaml # krimto server config

Path rules

  • Scope levels are exactly three: user, team, org. No nested teams, no sub-orgs. This is intentional — verified competitor Mem0 uses user/session/agent scopes (different model); Letta uses per-agent blocks (single-level). Three levels with named precedence is Krimto-specific.
  • The slug after the scope type is alphanumeric, dashes, dots, and at-signs. User identities use the OAuth claim format (typically local-part@domain).
  • Each fact file lives under exactly one scope folder. Moving a fact between scopes is git mv — the fact's id stays the same, its scope frontmatter field updates.
  • An organization has exactly one org/<slug>/ folder. Multi-org setups require separate Krimto instances.

Precedence rules

When a single retrieval query touches facts from multiple scopes that contradict each other, the precedence order is:

  1. user/<requester>/ — most specific wins. Alice's personal preferences override team defaults.
  2. team/<requester's-team>/ — team conventions override organization defaults.
  3. org/<requester's-org>/ — fallback baseline.

Precedence applies only to retrieval ranking, not to access control (access is binary per Gap 07). Implementation detail: the retrieval algorithm (Gap 04) boosts scores for matches in higher-precedence scopes.

Design decision — three fixed levels: Mem0 has user/session/agent; Letta has per-agent blocks; Hindsight has a four-network architecture without explicit hierarchical scope. None of these match Krimto's positioning. The user/team/org hierarchy is the dossier's Section 05 promise #02 — what no verified competitor ships as a primary primitive.
Cannot verify: Whether some teams will want nested teams (e.g., team/engineering/payments). The simple three-level model is chosen for v0.1 to ship faster. If nested teams turn out to be needed, the storage format supports them (it's just deeper folders) but the API and precedence rules would need extension.
04 Retrieval algorithm and hierarchical precedence Tier 1

memweave's pipeline, with scope boost.

The base retrieval algorithm is memweave's verified pipeline: hybrid BM25 + vector merge, threshold filter, temporal decay, MMR diversification. Krimto adds a hierarchical scope boost stage to implement the precedence rules from Gap 03.

Verified default — anchored directly to memweave production architecture

Pipeline

# Stage 1: parallel retrieval from both indexes bm25_results = FTS5_BM25(query, limit=50) vector_results = sqlite_vec_cosine(query_embedding, limit=50) # Stage 2: weighted merge (memweave's verified weights) merged_score = 0.7 * vector_score + 0.3 * bm25_score # Stage 3: threshold filter results = [r for r in merged if r.score >= 0.35] # Stage 4: temporal decay (memweave's verified pattern) for r in results: days_old = (now - r.updated).days r.score *= exp(-days_old / decay_half_life) # Evergreen exception: org/ scope is never decayed # Stage 5: KRIMTO-SPECIFIC — hierarchical scope boost for r in results: if r.scope.startswith(f"user/{requester}/"): r.score *= 1.5 # personal wins ties elif r.scope.startswith(f"team/{requester_team}/"): r.score *= 1.2 # team beats org # org/ scope: no boost (baseline) # Stage 6: MMR diversification final = mmr_select(results, lambda=0.7, k=10)

Parameter defaults

ParameterDefaultSource

Score threshold0.35memweave verified default
Temporal decay half-life30 daysmemweave configurable; 30 days is reasonable starting point

Evergreen exemption

Facts in org/ scope are exempt from temporal decay. Organizational standards (security rules, code style, compliance notes) do not "expire" the way personal notes do. This matches memweave's verified pattern: MEMORY.md and non-dated files are never decayed.

Verified anchor: The entire base pipeline (BM25 + vector merge with 0.7/0.3 weights, 0.35 threshold, exponential temporal decay, MMR with λ=0.7) is memweave's production architecture as documented in Towards Data Science April 2026 and confirmed in the github.com/sachinsharma9780/memweave source code. OpenClaw uses the same pattern (verified DeepWiki documentation February 2026). This is the single most directly transferable spec in this document. Source: towardsdatascience.com/memweave April 2026; deepwiki.com/openclaw/openclaw/7.3-memory-search February 2026
Design decision — Stage 5 (hierarchical scope boost): The personal/team/org boost multipliers are Krimto-specific. The 1.5x / 1.2x / 1.0x values are chosen to make the precedence implicit rather than absolute — a much more relevant team fact still wins over a marginally-relevant personal fact. Adjustable based on user feedback; the relative ordering (personal > team > org) is the architectural commitment.
Cannot verify: Whether the multiplicative boost approach is better than an additive offset or a hard-prefer-personal approach. memweave does not implement hierarchical scope, so this layer has no direct comparable benchmark. Should be measured against Krimto-specific user satisfaction after launch.
05 MVP definition (v0.1 scope) Tier 1

What ships first. What waits.

v0.1 of Krimto is the minimum surface that lets a single developer install it, write facts via Claude Code, and recall them across sessions. v0.1 ships without the web UI, without team features, without the hosted offering. v0.2 adds teams. v0.3 adds the web UI. v1.0 adds the hosted offering. This sequencing follows Hindsight's verified shipping pattern (December 2025 launch: single Docker, CLI-only, web UI deferred).

What v0.1 must actually do — acceptance test

  1. A developer runs docker run -d -p 8080:8080 -v ~/.krimto:/data ghcr.io/krimto-labs/server. Container starts in under 10 seconds.
  2. They add one entry to their Claude Code config pointing at http://localhost:8080.
  3. They ask Claude Code to remember a fact. Claude Code calls krimto_write. The fact appears as a markdown file at ~/.krimto/user/<identity>/<slug>.md.
  4. They restart Claude Code (clearing context). They ask a question related to the fact. Claude Code calls krimto_recall. The fact is returned in the top-3 results.
  5. They edit the markdown file directly in their text editor. They ask Claude Code the same question. The updated content is returned.

If all five steps work end-to-end on a single developer's laptop, v0.1 is shippable.

What v0.1 explicitly does NOT do

  • No team or org scopes. Storage paths are limited to user/<single-user>/.
  • No SSO, no multi-tenancy, no OAuth. Single API key in config.yaml.
  • No web UI. Configuration via config file; observation via the file system or git log.
  • No Cloud signup, no migration tooling. Self-host only.
  • No automatic fact extraction. Writes happen only when the agent calls krimto_write (Gap 11).
  • No supersede / history navigation tools. Edit markdown files directly in v0.1.

06 Authentication mechanism Tier 2

API keys for MCP. OAuth for humans.

Two authentication paths. MCP clients (Claude Code, Cursor, Codex) authenticate via API keys in their MCP server config. Humans accessing the web UI or hosted dashboard authenticate via OAuth providers (Google Workspace, GitHub, Microsoft Entra ID). The same identity model serves both paths.

Verified default — anchored to Langfuse and ByteRover

MCP client authentication (API keys)

Each user generates one or more API keys via the web UI (or via a CLI command for v0.1). The API key is included as a bearer token in MCP requests:

{ "mcpServers": { "krimto": { "url": "http://localhost:8080", "headers": { "Authorization": "Bearer krm_live_aBcD1234..." } } } }

API key format

  • Prefix: krm_live_ for production, krm_test_ for sandbox (Stripe pattern, verified standard).
  • Random body: 32 characters, base62, generated server-side at key creation time.
  • Stored server-side as Argon2 hash. Plain key shown only once at creation.
  • Each key carries one identity (the user who created it). API keys do NOT carry role independently — role is derived from the identity (see Gap 07).

Web UI authentication (OAuth)

For v0.3+ web UI and v1.0 Krimto Cloud, supported OAuth providers (anchored to Langfuse's verified provider list):

  • Google Workspace
  • GitHub
  • Microsoft Entra ID (formerly Azure AD)
  • Okta
  • Auth0

SAML and SCIM support are deferred to enterprise tier; they require additional engineering work and are anchored to Langfuse's Teams add-on tier (verified langfuse.com/enterprise).

Self-hosted bootstrap

For self-hosted v0.2+, the first admin is created via an environment variable at first container start:

docker run -d \ -p 8080:8080 \ -v ~/.krimto:/data \ -e KRIMTO_BOOTSTRAP_ADMIN=alice@acme.com \ -e KRIMTO_OAUTH_PROVIDER=google \ -e KRIMTO_OAUTH_CLIENT_ID=... \ -e KRIMTO_OAUTH_CLIENT_SECRET=... \ ghcr.io/krimto-labs/server

On first login matching the bootstrap email, the user is granted org admin role. Subsequent users are invited via the web UI.

Verified anchor: API-key-for-machine-clients + OAuth-for-humans is the standard split across Langfuse Cloud, Mem0 Cloud, ByteRover Cloud, and most modern SaaS. Langfuse Cloud Teams supports Google, GitHub, Azure AD, Okta, Auth0, AWS Cognito, Keycloak, JumpCloud — verified langfuse.com/enterprise. Stripe-style sk_live_/sk_test_ key prefixes are an industry standard for distinguishing environments. Source: langfuse.com/enterprise; stripe.com/docs/keys (industry-standard API key format)
Cannot verify: Whether SAML/SCIM is needed inside the first year. Verified pattern (Langfuse) gates these behind a paid Teams add-on at +$300/month. Krimto can follow the same pattern. Decision can be deferred until enterprise customers ask.
07 User / team / org data model Tier 2

Membership in YAML. Stored in git.

The user/team/org data model is stored as a YAML file at .krimto/members.yaml in the same git repository as the facts. This makes membership git-diffable, version-controlled, and reviewable via pull request — the same trust pattern as the facts themselves. The API server enforces access control by reading this file (cached, hot-reloaded on git pull).

Design decision — Krimto-specific, anchored to GitHub CODEOWNERS pattern

Membership file

# .krimto/members.yaml org: slug: acme name: "ACME Corporation" admins: - alice@acme.com teams: - slug: payments name: "Payments Team" members: - alice@acme.com - bob@acme.com - carol@acme.com leads: - alice@acme.com - slug: infrastructure name: "Infrastructure Team" members: - dave@acme.com - eve@acme.com leads: - dave@acme.com users: - email: alice@acme.com name: "Alice Anderson" created: 2026-05-22T14:32:00Z - email: bob@acme.com name: "Bob Brown" created: 2026-05-22T14:33:00Z

Access rules — server enforcement

The API server checks every request against these rules before reading or writing any markdown file. Folder permissions on the filesystem do not enforce access (the Atlan April 2026 verified failure mode — see dossier Section 13). The server is the enforcer.

Pseudocode for the access check:

def can_read(user, scope): if scope.startswith("user/" + user.email): return True # own user scope if scope.startswith("team/"): team_slug = scope.split("/")[1] return user.email in teams[team_slug].members if scope.startswith("org/"): return True # any member can read org scope return False def can_write(user, scope): if user.email in org.admins: return True # org admin writes anywhere if scope.startswith("user/" + user.email): return True # own user scope if scope.startswith("team/"): team_slug = scope.split("/")[1] return user.email in teams[team_slug].members return False

Membership changes

Adding or removing team members happens via the web UI (which writes to members.yaml and commits to git) OR via direct git pull request. Pull-request based membership changes are a deliberate Krimto feature — adding someone to a sensitive team can be code-reviewed before the change lands.

Verified anchor: Git-tracked membership is the same trust pattern as GitHub's CODEOWNERS file (verified github.com documentation): membership and ownership decisions stored as version-controlled text, reviewed via pull request, audited via git log. The pattern is universal across modern engineering practice. Source: docs.github.com/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners
Design decision — four roles, not more: Org admin / team lead / team member / org member is the minimum useful role set. Verified comparable (Langfuse) ships project-level RBAC with custom roles in their Teams tier; Krimto defers custom roles to a hypothetical enterprise tier. 08 Concurrency and write coordination Tier 2

Server-coordinated writes. Git as the commit log.

All writes go through the Krimto API server. The server is the single writer to git — agents never touch the git repository directly. Writes are serialized through an in-process queue, batched into commits, and pushed to the configured git remote on a schedule. This addresses the verified concurrency failure mode (Lanham Medium March 2026: "concurrent file writes can corrupt data — databases win under concurrent access").

Verified default — anchored to memweave's SQLite-as-coordinator pattern

Write flow

  1. Agent calls krimto_write via MCP. Request includes API key, scope, title, body.
  2. Server validates auth and access (Gap 06, Gap 07). Rejects if the requester cannot write to the scope.
  3. Server generates fact ID, sets created and updated timestamps, and assigns the author from the API key identity.
  4. Server writes to SQLite first (the coordination layer). The fact is persisted in the SQLite database with all metadata. If SQLite write fails, the operation is rejected.
  5. Server writes the markdown file to disk in the configured git working directory.
  6. Server stages the file in git (git add).
  7. Server returns success to the agent with the new fact ID. SQLite has the data; the markdown file exists; the index will pick it up on the next commit.
  8. Commit batcher runs periodically (default: every 30 seconds OR after 10 staged writes, whichever comes first). It executes git commit with a Krimto-generated commit message, then git push to the configured remote.

Commit message format

krimto: write [scope=team/payments] by alice@acme.com Title: Stripe webhook conventions Fact ID: fct_01j2k3m4n5p6q7r8s9t0v1w2x3 Tags: stripe, webhooks, payments Co-authored-by: Krimto-Server <krimto@acme.krimto.cloud>

The commit's git author is the Krimto server (a service account). The fact's human author is recorded both in the commit message and in the file's frontmatter. This makes git log --author=alice@acme.com work as expected when configured to read the frontmatter, while also preserving "this commit was machine-generated" auditability.

Conflict resolution

Conflicts only arise between Krimto server writes and external writes (a developer editing the markdown file directly in git, then pushing). The server detects conflicts on push:

  • If the conflict is in the body of a fact, Krimto surfaces it as a pending-review PR in the web UI rather than auto-merging.
  • If the conflict is in frontmatter (especially the id or created fields), Krimto rejects the external edit and requires manual resolution. This is intentional: frontmatter is server-authoritative.
  • The default git pull strategy is --rebase, then re-apply staged Krimto writes. If rebase fails, server enters read-only mode and alerts the admin.
Verified anchor: memweave's verified architecture uses SQLite as the coordination layer: "SQLite handles write coordination; markdown gets the final committed state" (Towards Data Science April 2026). Krimto follows the same pattern, extended with a periodic git commit batcher for the markdown persistence layer. The "all writes go through the server" approach is also Hindsight's pattern (verified github.com/vectorize-io/hindsight architecture). Source: towardsdatascience.com/memweave April 2026; github.com/vectorize-io/hindsight
Design decision — batched commits, not per-write commits: Per-write commits would create 100+ commits per active team-hour, which is git-history noise. Batching every 30 seconds or every 10 writes is a balance between durability (no data loss) and history hygiene. Adjustable. memweave does not have a git layer at all (single-machine SQLite), so this is Krimto-specific design.

09 Index maintenance Tier 2

SQLite + sqlite-vec. Embed only on change.

The retrieval index lives in a single SQLite database file. Schema is anchored to memweave's verified production schema. The index updates incrementally on each write; full rebuild is possible but rarely needed. Embeddings use OpenAI's text-embedding-3-small by default (anchored to Mem0 and Hindsight standards), with caching keyed on content hash.

Verified default — anchored directly to memweave SQLite schema

SQLite schema

-- Anchored to memweave's verified production schema CREATE TABLE facts ( id TEXT PRIMARY KEY, -- ULID scope TEXT NOT NULL, title TEXT NOT NULL, body TEXT NOT NULL, author TEXT NOT NULL, created TIMESTAMP NOT NULL, updated TIMESTAMP NOT NULL, tags TEXT, -- JSON array source TEXT, supersedes TEXT, -- JSON array of fact IDs expires TIMESTAMP, body_hash TEXT NOT NULL -- SHA-256 of body for cache ); -- FTS5 full-text index for BM25 CREATE VIRTUAL TABLE facts_fts USING fts5( title, body, tags, content='facts', content_rowid='rowid' ); -- sqlite-vec for cosine similarity CREATE VIRTUAL TABLE facts_vec USING vec0( fact_id TEXT PRIMARY KEY, embedding FLOAT[1536] -- text-embedding-3-small dimension ); -- Embedding cache: only re-embed when body changes CREATE TABLE embedding_cache ( body_hash TEXT PRIMARY KEY, embedding BLOB NOT NULL, created TIMESTAMP NOT NULL );

Write-path index update

  1. Compute body_hash = SHA-256(body).
  2. Check embedding_cache for body_hash. If hit, reuse the cached embedding.
  3. If miss, call OpenAI text-embedding-3-small with the body text. Store result in embedding_cache.
  4. Insert into facts table.
  5. FTS5 automatically picks up the row via the content= trigger.
  6. Insert into facts_vec with the (possibly cached) embedding.

External-edit detection

When a developer edits a markdown file directly (outside the API) and the change arrives via git pull, the server detects this on its next pull cycle:

  1. Server runs git pull --rebase periodically (default: every 60 seconds).
  2. For each changed file in the pull, server reads the frontmatter to find the id.
  3. Server compares the file's current body_hash against the database row.
  4. If different, server re-indexes: re-embed (with cache check), update facts row, refresh facts_vec.
  5. FTS5 updates automatically via the content trigger.

Full rebuild

A full rebuild is available via admin command: krimto reindex. It walks every markdown file in the repository, drops and recreates the facts, facts_fts, and facts_vec tables, then re-indexes everything. The embedding_cache is preserved across rebuilds, so re-indexing is cheap if content has not changed. Realistic time: roughly 1 second per 100 facts on commodity hardware (anchored to memweave's published throughput).

Verified anchor: The complete SQLite schema (chunks, chunks_fts via FTS5, chunks_vec via sqlite-vec, embedding_cache keyed on hash, files for change detection) is memweave's verified production schema documented at github.com/sachinsharma9780/memweave and in Towards Data Science April 2026. Krimto uses the same schema with field names adapted to "facts" instead of "chunks." 11 Agent write workflow Tier 2

Explicit writes only. No silent extraction.

Krimto does not extract facts automatically from conversation history. Agents call krimto_write explicitly when they have something durable to record. This is a deliberate divergence from Mem0 and ByteRover (which extract automatically) and aligns with Hindsight's retain pattern. The reasoning: hierarchical-team-memory requires attributable, intentional facts — silent extraction creates facts no human reviewed.

Design decision — diverges from Mem0 / ByteRover, aligns with Hindsight

When agents should call krimto_write

The agent prompt (in the MCP tool description) instructs the agent to call krimto_write in these situations:

  • The user explicitly says "remember this," "save this," "make a note," or equivalent.
  • The agent learns a non-obvious, durable fact (a deprecation, an environment-specific constraint, a team convention) that would benefit future sessions.
  • The user corrects the agent on something the agent should not repeat the mistake on.

When agents should NOT call krimto_write

  • Conversational context (small talk, current-session reasoning).
  • Facts that are already in the user's existing knowledge base (the agent should call krimto_recall first to check).
  • Speculative or unverified information.

Scope selection

The agent decides which scope to write to based on the conversation context and the user's identity:

  • Personal scope is the default. If the user says "remember that I prefer X" or the fact is about the individual user's preferences, write to user/<identity>/.
  • Team scope when the user explicitly says "remember this for the team" or the fact is about a shared system (team's API conventions, deployment rules).
  • Org scope only when the user is an org admin and explicitly requests organization-wide knowledge.

If the agent is unsure, it writes to the user's personal scope. The user can later promote the fact to team scope via krimto_supersede + git mv (web UI in v0.3+, manual git operation in v0.1-v0.2).

14 Source / provenance tracking Tier 3

One field. URL or stable ID.

The source field in fact frontmatter records where the fact came from. It is optional and free-form, but encouraged. Provenance is what lets the team trust a fact — and lets them re-check it when the source changes.

Design decision — Krimto-specific, minimal scope

Source field format

The source field is a string. Common formats:

  • URL: "https://stripe.com/docs/webhooks" — link to documentation, blog post, etc.
  • GitHub PR / issue: "github.com/acme/payments-service/pull/421" — links to a code review where the fact was decided.
  • Slack thread: "slack://acme/C0123456/p1700000000" — for facts that originated in a conversation.
  • Meeting / decision: "decision:2026-05-15-stripe-webhook-review" — for facts that came from a meeting; the slug links to wherever that meeting is documented.
  • None: field omitted entirely — for facts the author cannot or does not need to source.

What source is NOT

  • Not a foreign key. Krimto does not fetch or validate the source URL.
  • Not required. Many facts (preferences, conventions) do not have an external source.
  • Not searchable as content. Source is metadata, not body text.

Stale-source detection (v1.1+, deferred)

A potential future feature: Krimto periodically fetches the source URL (when it's a URL) and flags the fact if the source returns 404 or has been substantially modified. This would help teams identify facts that may be based on stale documentation. Not in v0.3 scope. Anchored to the verified problem (deprecation drift) that Mem0 and Hindsight do not address.

Design decision — free-form string, not structured: Forcing a structured source object (type, URL, identifier) would create friction and reject sources that don't fit the schema. A free-form string lets the team source things however they need. The cost is that source-based search and validation are harder; the benefit is that no fact is rejected for not having a "valid" source.

Retry semantics

Two status codes are explicitly retryable: 429 (rate limited) and 503 (temporarily unavailable). Both include a Retry-After header with seconds to wait. All other 4xx responses are client errors and should NOT be retried without correction. 500 is server error and may be retried with exponential backoff, but the underlying issue should be investigated.

Verified anchor: JSON-RPC 2.0 specification defines the error object structure (code, message, optional data) with reserved code range -32768 to -32000 for protocol-level errors and -32000 to -32099 for server-defined errors. MCP specification (modelcontextprotocol.io) uses this pattern. HTTP status codes follow RFC 7231 (HTTP/1.1 semantics). Langfuse's API documentation uses identical error envelope structure (verified langfuse.com API docs). Source: jsonrpc.org/specification; modelcontextprotocol.io; IETF RFC 7231; langfuse.com/api
Design decision — custom codes -32000 through -32003: These are within the JSON-RPC reserved server-error range and are Krimto-specific. They distinguish between auth failure, permission failure, rate limiting, and not-found — distinctions a generic -32603 Internal Error would lose. Anchored to the same approach used in other MCP server implementations.
Cannot verify: Whether clients will actually consume the data field on errors or rely only on message. The structured data field is included because it enables programmatic recovery (e.g., showing which field validation failed), but adoption depends on client implementation.
17 Health check endpoints Tier 2 · v002

Liveness for orchestrators. Readiness for traffic.

Two endpoints, both following Kubernetes liveness/readiness conventions. /health/live confirms the server process is running. /health/ready confirms the server is ready to accept traffic — SQLite reachable, git remote reachable, index loaded. Container orchestrators use these for rolling updates, autoscaling, and failure recovery.

Verified default — anchored to Kubernetes liveness/readiness pattern

Endpoints

EndpointPurposeResponse
GET /health/live Is the server process running and the HTTP listener responsive? Should return 200 immediately if the process is alive. Used by orchestrator to decide whether to restart the container. 200 / 500
GET /health/ready Is the server ready to accept traffic? Checks: SQLite connection open, index built, git remote reachable (if configured). Used by orchestrator to decide whether to route traffic. 200 / 503
GET /health Alias for /health/ready. Common convention for simpler deployments that don't distinguish live/ready. 200 / 503

Response format

Both endpoints return JSON with a consistent schema. Liveness is intentionally minimal (any work in the liveness probe risks false negatives that trigger unnecessary restarts):

// GET /health/live — minimal, no dependencies checked HTTP/1.1 200 OK { "status": "alive", "version": "0.1.0", "uptime_seconds": 8472 } // GET /health/ready — checks dependencies HTTP/1.1 200 OK { "status": "ready", "version": "0.1.0", "checks": { "sqlite": { "status": "ok", "latency_ms": 1 }, "index": { "status": "ok", "fact_count": 1247 }, "git_remote": { "status": "ok", "last_sync": "2026-05-22T14:30:00Z" } } } // GET /health/ready — when not ready HTTP/1.1 503 Service Unavailable { "status": "not_ready", "checks": { "sqlite": { "status": "ok" }, "index": { "status": "building", "progress": 0.34 }, "git_remote": { "status": "ok" } } }

What each check verifies

CheckWhat it tests
sqliteSQLite database file is open and a simple SELECT 1 succeeds within 100ms.
indexIndex is loaded; reports fact count. During startup or full rebuild, returns building status with progress.
git_remoteFor configurations with a git remote, verifies the remote is reachable. Records the timestamp of the most recent successful sync. Failures here do not mark unready — Krimto is still useful even if temporarily unable to push.

When readiness returns 503

  • SQLite check failed (database locked, disk full, file corrupted)
  • Index is still building from initial git clone or full rebuild
  • Server is in the brief startup window before all subsystems are loaded

Liveness returning 500 (which is rare) indicates the process is stuck — orchestrator should restart. Krimto should not return 500 from liveness for transient issues; that's what readiness is for.

Verified anchor: The split between liveness and readiness probes is the Kubernetes-recommended pattern documented at kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes. Hindsight, Langfuse, and Mem0 all ship /health or /healthz endpoints (verified across their respective documentation). The JSON response format with per-check status is the same shape used by Spring Boot Actuator's /actuator/health and by Kubernetes itself — verified universal pattern. Source: kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes; standard health check pattern across modern services
Design decision — git remote check does not block readiness: A temporarily unreachable git remote (network blip, GitHub outage) should not take Krimto offline. Reads still work from local SQLite; writes can still queue. The check is reported in the health response for observability but doesn't toggle the ready/not-ready bit. This is intentional — the alternative (taking Krimto down whenever GitHub has a brief incident) is worse than the current trade-off.
Cannot verify: Whether 100ms is the right SQLite latency threshold. Anchored to standard health check timeouts but should be measured under realistic load.

Self-hosted defaults

  • Configurable via config.yaml:
    rate_limits: enabled: false # enable globally per_api_key: 600 # requests per minute per API key per_ip: 3000 # requests per minute per source IP burst: 100 # allow short bursts above the steady rate

Response headers (always included)

Whether rate limiting is enabled or not, Krimto always returns these headers so clients can adapt:

X-RateLimit-Limit: 600 X-RateLimit-Remaining: 587 X-RateLimit-Reset: 1716567480

The Reset header is a Unix timestamp indicating when the current rate-limit window resets. When limit is disabled, Limit reports a very large number and Remaining always matches.

429 response

HTTP/1.1 429 Too Many Requests Retry-After: 23 X-RateLimit-Limit: 600 X-RateLimit-Remaining: 0 X-RateLimit-Reset: 1716567480 { "error": { "type": "rate_limit_exceeded", "message": "Rate limit exceeded. Retry after 23 seconds.", "details": { "limit": 600, "window_seconds": 60, "retry_after_seconds": 23 } } }

What counts as a request

  • Each MCP tool call (one call to krimto_write, krimto_recall, etc.) counts as one request.
  • Each REST API call counts as one request.
  • Health check endpoints (/health/*) do NOT count — orchestrators poll these continuously and including them would create rate-limit thrash.
  • Internal git pull operations do NOT count — these are server-internal.

Source: langfuse.com/enterprise; IETF RFC 6585; standard X-RateLimit-* convention across major APIs

19 Telemetry policy Tier 2 · v002

No telemetry by default. Opt-in, transparent if enabled.

Self-hosted Krimto reports no telemetry by default. The Apache 2.0 OSS positioning in dossier Sections 05, 10, and 12 depends on user trust, and silent telemetry is verified to break that trust. If an operator opts in, exactly what is collected is documented and inspectable. Krimto Cloud telemetry is separate — Cloud inherently has access to usage data and that policy is governed by the Cloud Terms of Service.

Verified default — anchored to Cipher (no telemetry) + Langfuse self-hosted (opt-in)

Self-hosted default

  • No telemetry. No phone-home. No usage reporting. Self-hosted Krimto does not make outbound network calls to Krimto-controlled servers in default configuration.
  • The only outbound calls in default config are: (a) git push/pull to the configured git remote, (b) embedding API calls to the configured embedding provider, both of which are explicitly user-configured and serve direct user needs.
  • This matches Cipher's verified policy: "no account, no cloud, no telemetry."

Optional opt-in

Operators may enable anonymous usage telemetry to help Krimto maintainers understand deployment patterns:

telemetry: enabled: false # default; set to true to opt in endpoint: "https://telemetry.krimto.com" include: - version # Krimto version string - install_id # random UUID, locally generated - deployment_type # self-hosted | cloud - fact_count_bucket # bucketed: 0-100, 100-1K, 1K-10K, 10K+ - team_count_bucket # bucketed: 1, 2-5, 6-20, 20+ - active_user_count_bucket # bucketed: 1, 2-10, 11-50, 50+

What is NEVER collected, even with opt-in

  • No fact content. Markdown bodies, titles, tags — none of these are transmitted under any configuration.
  • No user identities. Email addresses, OAuth claims, member names — never transmitted.
  • No scope paths. Team names, org names, user identifiers in paths — never transmitted.
  • No git remote URLs or repository names.
  • No retrieval queries. What users search for is private.
  • No IP address logging beyond what is needed for the immediate HTTP response.

Inspectability

The telemetry payload is logged locally in plaintext to logs/telemetry-outbound.jsonl before transmission. Operators can inspect exactly what was sent. This is the verified Langfuse self-hosted pattern: every telemetry event is auditable.

Krimto Cloud telemetry (separate policy)

Krimto Cloud is the hosted service. The Cloud server inherently has access to usage patterns of its own customers — that's intrinsic to running a hosted service. Cloud telemetry policy is governed by the Krimto Cloud Terms of Service, which must be explicit about:

  • What's collected (for billing, capacity planning, abuse detection)
  • What's never collected (fact content, retrieval queries, member identities beyond billing-required fields)
  • Data retention windows
  • The customer's right to export and delete their data (anchored to GDPR Article 15 and 17 requirements)

The Cloud Terms of Service are a separate document from this build spec. Their content is informed by the same trust principles — explicit, narrow, inspectable — but the legal text is governed by counsel, not by the build spec.

Verified anchor: Cipher (ByteRover open source) ships with explicit "no account, no cloud, no telemetry" policy (verified github.com/campfirein/cipher README). Langfuse self-hosted offers opt-in telemetry with documented collection at langfuse.com/self-hosting/telemetry (verified). The "never collect content, queries, or identities" boundary is the verified standard across reputable OSS infrastructure projects (PostgreSQL, Redis, SQLite all collect zero application data in their tooling). Source: github.com/campfirein/cipher README; langfuse.com/self-hosting/telemetry; standard OSS infrastructure project privacy norms
Design decision — opt-in, not opt-out: Some OSS projects default telemetry on with an opt-out path. This is verified to generate user backlash (verified Homebrew telemetry controversy 2016; verified Atom telemetry controversy 2017). Krimto follows the safer pattern: off by default, on only when explicitly enabled. Trades a smaller telemetry sample size for trust.
